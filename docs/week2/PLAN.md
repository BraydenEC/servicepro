## 1. The risk that defines this week

Weeks 0 and 1 both failed the same way: correct code, unconfigured environment. **Week 2's
characteristic failure is completely different, and worse.**

This assignment asks for market research — competitor pricing, adoption benchmarks, evidence
the problem is real. That is exactly the material a language model will invent fluently and
confidently. A fabricated statistic looks identical to a real one, reads more quotably, and
cannot be caught by any test I can run.

**Design consequence, decided up front:** verification is a first-class field, not a footnote.

- Every competitor row and every benchmark carries `source_url` and `verified_on`.
- A claim with no source renders visibly marked as unverified — it does not silently pass as fact.
- Pricing carries the date it was checked, because pricing changes.
- I will not generate a market-size figure, adoption percentage, or growth rate unless it can be
  attributed. Where a number would strengthen the argument but cannot be sourced, the page says so.

Week 0's lesson was *a deploy is not a configuration*. Week 2's is **a plausible number is not a
fact** — and unlike the last two, this one has no automated check. The only defense is structure.

## 4. Proposed research content

### The argument the page has to make

ServicePro claims freelancers juggle disconnected tools. Week 2 must show that (a) the problem is
real, (b) tools exist, and (c) a gap remains. The **gap is the interesting part**, and for a
Mexican business course there is a strong, genuine one:

> Global freelance tools handle invoicing as a PDF. Mexican freelancers cannot invoice with a PDF
> — they must issue a **CFDI** through the SAT, via an authorized PAC, with an RFC and a digital
> certificate. Harvest, Bonsai, and FreshBooks do not do this. Mexican accounting tools do CFDI
> but are built for accountants, not project tracking.
>
> So a Mexican freelancer runs *two* systems: a foreign tool for project and time tracking, and a
> local tool for the invoice that is legally required. That is the gap.

**This must be verified before it is claimed.** It matches how Mexican electronic invoicing works
as I understand it, but the specifics — CFDI version, retention percentages, RESICO rules,
whether any listed competitor has added CFDI support — need checking against current SAT
documentation and each vendor's own site. Every such claim will carry a source or be marked
unverified.

### Competitors and substitutes — 8 minimum

Drafted as categories to research, not as findings:

| Category | Candidates |
|---|---|
| Global freelance suites | Bonsai, FreshBooks, Harvest |
| Time tracking | Toggl Track, Clockify |
| Project management | Notion, Trello |
| Mexican invoicing / CFDI | Facturama, Alegra, Contpaqi, Factura.com |
| **Substitutes** | Excel/Google Sheets, WhatsApp + notes app, pen and paper |

**Substitutes deserve equal weight.** The real incumbent is a spreadsheet, not a competitor
product — that is the actual thing being displaced, and saying so is more honest than listing
only funded startups.

### Risk map

Five to seven risks plotted on likelihood × impact. Candidates:

- A Mexican invoicing tool adds project tracking *(high impact — closest to the thesis)*
- A global suite adds CFDI support
- CFDI regulations change, invalidating the integration
- Freelancers keep using spreadsheets because they are free
- Single-developer capacity

The honest one belongs on the map: **the strongest risk is that the gap closes from the Mexican
side**, since a CFDI vendor adding a project table is easier than a US vendor implementing
Mexican tax law.

## 5. Proposed architecture

### Page structure — `/research`
```
Header — the claim being tested
  ↓
Research intake form ──────────▶ structured record (reuses the Week 1 extraction pattern)
  ↓
Benchmark cards — 5 global examples, each with source + date checked
  ↓
Mexico localization panel — the CFDI gap, sourced
  ↓
Competitor & substitute table — 8+, client-side filter/search, verification badge per row
  ↓
Risk map — likelihood × impact grid
  ↓
Saved research records — from Supabase
```

### Data model — `research_records`

| Column | Type | Notes |
|---|---|---|
| `id` | uuid PK | |
| `raw_input` | text | Original note, kept for auditability |
| `title` | text | |
| `category` | text | CHECK: `competitor`, `substitute`, `benchmark`, `risk`, `insight` |
| `region` | text | CHECK: `global`, `mexico` |
| `summary` | text | |
| `source_url` | text **nullable** | **NULL means unverified, and renders as such** |
| `verified_on` | date nullable | |
| `confidence` | text | CHECK: `verified`, `reported`, `estimated` |
| `extractor` | text | `model` or `heuristic` — same provenance discipline as Week 1 |
| `prompt_version` | text | |
| `created_at` | timestamptz | |

`source_url` being nullable is deliberate and is the whole point: the schema makes an unsourced
claim *representable but visible*, rather than either impossible or invisible.

### Reuse from Week 1
The null-safe Supabase client, the extractor-with-fallback pattern, the provenance columns, and
the zod validation approach all carry over unchanged. **Net new dependencies: zero.**

### The one architectural first
Filter/search must run client-side for instant feedback, so the table becomes a Client Component
receiving server-fetched data as props. The page stays a Server Component; only the interactive
table is a client island.

## 7. 🔴 What only you can do

### The human validation conversation

This is a hard requirement and cannot be produced, simulated, or written for you. Find one
person — a freelancer, contractor, designer, or consultant, ideally in Mexico — and have a real
conversation.

**Suggested questions** (open, non-leading — you want to hear that you are wrong if you are):

1. How do you currently track what clients owe you?
2. Walk me through what happens between finishing work and getting paid.
3. What do you use to invoice? How long does it take?
4. *(Mexico)* How do you handle CFDI/facturación? Is it the same tool?
5. What is the most annoying part of the admin side?
6. Have you tried a tool for this? What happened?
7. What would have to be true for you to switch?

**Capture:** who they are, when you spoke, what they actually said, and — most valuable —
**anything that contradicted your assumptions.** A conversation that confirms everything is
usually a conversation with leading questions.

I will provide a structured template to record it in.
